# Runbook — Token Certificates (Signing & Encryption)

> **Status:** ACTIVE. Created 2026-08-16 after a PFX incompatibility investigation.
> Scope: generation, deployment, rotation and troubleshooting of the X.509 certificates
> used by the identity server to sign (JWT/JWKS) and encrypt (JWE) OAuth/OIDC tokens.

## Overview

| Certificate | File | Purpose | Typical validity | Common Name |
|---|---|---|---|---|
| **Signing** | `certificate.pfx` | Signs JWTs; publishes JWKS | 10+ years | `*-identity-signing` |
| **Encryption** | `certificate-encryption.pfx` | Decrypts JWE access tokens | 10+ years | `*-identity-token-encryption` |
| **Vault KEK** | `vault-kek.pfx` | Protects the vault's DataProtection key ring | 10+ years | `*-identity-vault-kek` |

## ⚠️ CRITICAL — PFX Runtime Incompatibility

**The .NET 10.0.10 runtime used in production rejects PFX files that were not
generated by the same runtime**, regardless of password or PKCS#12 parameters.
This was discovered when attempting to deploy a separate encryption certificate.

### What does NOT work (tested and confirmed)

| Generation method | Server result |
|---|---|
| `openssl req` + `openssl pkcs12 -export` (any combination of `-certpbe`, `-keypbe`, `-macalg`) | Rejected: "password may be incorrect" |
| .NET SDK `CertificateRequest` + `Export(Pkcs12)` running under SDK 10.0.302 | Rejected: "password may be incorrect" |
| Any PFX with a password different from the original certificate's | Rejected: "password may be incorrect" |

### What DOES work

| Method | Context |
|---|---|
| The original `certificate.pfx` (generation method unknown) | Has always worked in production |
| .NET `Export(Pkcs12)` loaded by the **same runtime instance** | Round-trip verified locally |

### Root cause hypothesis

The runtime-only installation applies stricter `Pkcs12LoaderLimits` than the
SDK. The original certificate predates these limits or was produced by a tool
that generates a PKCS#12 structure that passes them.

## Recommended generation process

### Option A (RECOMMENDED) — Generate on the target server

Add a CLI command to the server binary:

```bash
# On the server (uses the SAME runtime that will load the cert):
/opt/dotnet/dotnet Server.dll --generate-encryption-cert \
    --output /opt/app/certificate-encryption.pfx \
    --password "NEW_PASSWORD"
```

This guarantees compatibility **by construction** — the certificate is
generated by the same runtime that will load it.

**Implementation sketch** (in `Program.cs`):
```csharp
if (args.Contains("--generate-encryption-cert"))
{
    var output = GetArg(args, "--output") ?? "certificate-encryption.pfx";
    var password = GetArg(args, "--password")
        ?? throw new ArgumentException("--password is required");

    var rsa = RSA.Create(3072);
    var request = new CertificateRequest(
        "CN=token-encryption",
        rsa, HashAlgorithmName.SHA256, RSASignaturePadding.Pkcs1);
    request.CertificateExtensions.Add(
        new X509KeyUsageExtension(
            X509KeyUsageFlags.KeyEncipherment | X509KeyUsageFlags.DataEncipherment,
            critical: true));
    using var cert = request.CreateSelfSigned(
        DateTimeOffset.UtcNow.AddMinutes(-5),
        DateTimeOffset.UtcNow.AddYears(10));
    File.WriteAllBytes(output, cert.Export(X509ContentType.Pkcs12, password));
    return;
}
```

### Option B (WORKAROUND) — Self-contained generator

```bash
# Locally:
dotnet publish -c Release -r linux-x64 --self-contained -o /tmp/cert-gen
scp /tmp/cert-gen/cert-gen user@server:/tmp/

# On the server:
/tmp/cert-gen  # generates and saves the PFX
```

**Note:** The binary must be truly self-contained (`--self-contained`).
A framework-dependent publish will not work on a server without the SDK.

### Option C (NOT RECOMMENDED) — Reverse-engineer the original

```bash
# On the server, extract the internal structure of the working cert:
openssl pkcs12 -in /opt/app/certificate.pfx \
    -passin pass:"$SIGNING_PASSWORD" -info -nokeys 2>&1
```

This is fragile: the difference may be in any ASN.1 attribute and can
change between runtime versions.

## Deployment procedures

### 1. Signing certificate rotation

```bash
# Generate new cert (see options above)
# Copy to server:
scp certificate-new.pfx user@server:/opt/app/

# Configure overlap (old cert stays in JWKS during transition window):
# appsettings:
#   "SigningPaths": ["certificate.pfx", "certificate-new.pfx"]
#   "SigningPath": "certificate-new.pfx"        ← new cert is active
#   "SigningPassword": "new-cert-password"

# Update secrets:
# SUFFICIT_SECRET_IDENTITY_CERTIFICATES_SIGNING_PASSWORD=new_password

# Restart:
systemctl restart app-service
```

### 2. Encryption certificate (separation from signing)

```bash
# Generate encryption cert (see options above)
scp certificate-encryption.pfx user@server:/opt/app/

# appsettings:
#   "EncryptionPath": "certificate-encryption.pfx"
#   "RequirePurposeSeparation": true

# secrets:
# SUFFICIT_SECRET_IDENTITY_CERTIFICATES_ENCRYPTION_PASSWORD=encryption_password

# Restart:
systemctl restart app-service
```

### 3. Vault KEK rotation

The vault KEK wraps the DataProtection key ring that protects secrets at
rest. It must be a **dedicated** certificate — never the signing cert.

```bash
# Generate KEK cert (RSA-3072, 10+ years)
# The vault handles re-encryption of wrapped DEKs automatically during rotation

# appsettings:
#   "Vault": {
#     "Enabled": true,
#     "KeySource": "certificate",
#     "CertificatePath": "/etc/app/vault-kek.pfx"
#   }

# secrets:
# SUFFICIT_SECRET_VAULT_KEK_CERTIFICATE_PASSWORD=kek_password
```

## Troubleshooting

### Error: "The certificate data cannot be read with the provided password"

**Root cause:** See [PFX incompatibility section](#critical--pfx-runtime-incompatibility).

1. Verify the password is correct:
   ```bash
   source /etc/app/vault-secrets.env
   openssl pkcs12 -in /opt/app/certificate.pfx \
       -passin pass:"$SIGNING_PASSWORD" \
       -nokeys -clcerts | openssl x509 -noout -subject
   ```

2. If openssl loads it but the application does not → **PFX format
   incompatibility** (the cert was generated by an incompatible tool)

3. **Fix:** regenerate using Option A or B above

### Error: "No signing certificate configured"

The certificate is missing or the path is wrong:
```bash
grep -E "SigningPath|EncryptionPath" /opt/app/appsettings.json
ls -la /opt/app/*.pfx
```

### Error: "Certificate purpose separation requires different certificates"

`RequirePurposeSeparation` is enabled but signing and encryption point to
the same file (identical thumbprints):
```bash
openssl pkcs12 -in certificate.pfx -passin pass:"PASS" -nokeys -clcerts \
    | openssl x509 -noout -fingerprint -sha256
openssl pkcs12 -in certificate-encryption.pfx -passin pass:"PASS" -nokeys -clcerts \
    | openssl x509 -noout -fingerprint -sha256
# Fingerprints MUST be different
```

## Best practices

1. **Generate on the server** (or use self-contained) — never with OpenSSL CLI
2. **Separate certificates by purpose** — signing ≠ encryption ≠ vault KEK
3. **Validity ≥ 10 years** to minimize rotation frequency
4. **RSA-3072 minimum** (FAPI 2.0 compatible when combined with PS256/ES256)
5. **Unique password per certificate** — the secrets boundary is per-cert
6. **Back up certificates AND passwords** in a secure location (not in the repo)
7. **Use overlap for signing rotation** — keep the old cert in JWKS via
   `SigningPaths` during the transition window
